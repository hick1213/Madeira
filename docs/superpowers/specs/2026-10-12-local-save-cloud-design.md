# Local-game saves in iCloud Drive

The user requested save synchronization for locally imported games, with upload/download controls in Settings and confirmation before overwriting. The proposed implementation uses one explicitly chosen save directory per local game, rather than restoring the existing backup of every Windows user's AppData. That scope was presented as the recommended option; the user's preference question remains pending. Core snapshot validation and safe restoration are independent of that UI choice.

No storefront, DRM, account-token or Steam Cloud changes are required. Games remain local library entries. Steam and Epic entries are excluded from the local-game selection. Actual saves are configured by the user, not guessed from the executable name. Initial supported locations are a game's directory/subdirectory or a dedicated game subdirectory under a Wine user's Documents, Saved Games or AppData roots; selecting a whole user, Windows drive or generic AppData root is disallowed.

Settings has a Local game saves page: choose an iCloud Drive folder through Files, select a local game and its actual save directory, then Upload saves or Download saves. A second device can choose an existing cloud backup and map it to that device's configured game directory. Persist the folder's minimal bookmark and restart scoped access for each coordinated operation. No native private iCloud container or new signing entitlement is registered. Only the selected Files folder is accessed. Writes are reported as written to the selected folder, waiting for the provider to upload, unless Apple explicitly reports completion; disk success alone is not server success.

Save backups use an independent bounded v1 JSON archive with named file data and SHA-256, not the old ZIP importer. Limits: 1,024 files, 16 MiB per file, 64 MiB decoded total, 96 MiB archive input. Reject malformed versions, names, dot traversal, control characters, colon/backslash, Windows case-equivalent duplicate paths, conflicting file/directory paths, links, hardlinks and changed reads. Empty save directories are valid restore targets; empty uploads report no saves.

Local reads start at the OS-provided Documents capability, traverse raw relative paths with openat/O_NOFOLLOW and do not resolve symlinks. Restoration validates the complete incoming archive before any destination mutation, checks the expected local fingerprint again after confirmation, backs up original files in Documents/iCloud Save Backups, stages a complete merged tree preserving unrelated files, then replaces the configured directory atomically using APFS rename swap. Failure must preserve or restore the original tree; if unsupported, fail without per-file partial replacement. Retain local backups. Confirmation cancellation makes no save/cloud writes.

Cloud uploads are immutable unique-version files; older versions are retained. When a different cloud version already exists, confirm replacement of the current cloud version before writing a new version. Downloads select a version and show file counts/overwrites before confirmation. Revalidate local and cloud fingerprints before commit; a change requires fresh confirmation. Different devices can have different Library UUIDs, so the downloaded backup's cloud-game UUID becomes the local configuration's selected cloud slot only after explicit mapping. No concurrent remote-version deletion is attempted.

Every read/write or pending confirmation holds GameSessionWork's exact save-operation token, which pauses nonessential downloads/scans and prevents game startup. Acquiring while launch/game work is active fails. Token release happens in success, failure, cancellation and page dismissal. No save snapshot is taken while Wine/server still writes.

Host tests exercise the actual core against exact task-owned APFS fixtures: traversal/symlink/hardlink/case collision, size/hash corruption, unchanged cancellation, changed destination fingerprint, original backup, merged files and failed swap. iOS build and picker/bookmark/coordinator paths are checked separately. Actual iCloud permission, upload completion, second-device download and UI confirmation require the user's real Files/iCloud interaction and cannot be claimed from local tests.
